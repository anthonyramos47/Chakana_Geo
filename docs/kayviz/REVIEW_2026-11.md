# kayviz review — diagnosis and improvement plan (2026-11-11)

Scope: the whole library (`kayviz/src/kayviz`, ~6 500 lines: Python server/runtime and
the three.js frontend), read in full, plus measurements on the Dupin playground and the
studio demo (MacBook Pro M1 Pro, 16 GB, Vivaldi). "Verified" = reproduced or measured;
"code" = follows directly from the code, not reproduced.

## 1. Where time and memory go (Dupin playground, Resolution 200)

| stage | time | size |
|---|---|---|
| user geometry (`build()`) | 0.01 s | — |
| kayviz serialisation (numpy → Python lists) | 0.27 s | 60–90 MB of Python objects |
| `json.dumps` | 0.45 s | 27.6 MB of text |
| same arrays as raw float32/int32 | — | 6.7 MB (≈2 MB without the duplicated edges) |
| full round trip, slider → new picture | 1.7 s | — |

Payload breakdown: the cyclide's edge coordinates are sent **twice** (9.5 MB in the mesh's
`poly_edge_verts`, 9.5 MB again as the `edge_child`), each 4× the vertex data, and every
float32 is written with 17 digits (`0.30000001192092896`). The cyclide's vertices are 2.4 MB.

GPU memory (Vivaldi GPU process, one tab): plain 1.2 GB, studio +0.7–1.0 GB, studio at
2× save resolution 4.5 GB. On Apple silicon this is system RAM. The two freezes of
2026-11-10/11 were WindowServer watchdog hangs with ~40 GB of footprint on 16 GB, the
largest process a 7.9 GB Vivaldi helper. Fixed already (uncommitted): studio releases its
buffers when switched off, saves capped at 12 Mpx, shadow map 2048.

Not leaking: the scene buffer in Python (keyed by name), object disposal in the viewer,
JS heap across a 30-event slider drag (stays < 170 MB after GC).

## 2. Bugs

### Critical — can freeze or crash

| # | bug | where | status |
|---|---|---|---|
| B1 | User callbacks (and sync GUIApp actions) run **on the server's event loop**: a 1.7 s Dupin update freezes the whole server — every tab, pings, screenshots, `show()`'s wait — for its duration. | `callback_app.py:150`, `app.py:120` | code |
| B2 | Every run of a script opens a **new tab**; old tabs reconnect forever (backoff ≤ 10 s) to the new server on the same port. N runs → N live tabs, each receiving every update, rendering at 60 fps and holding GPU memory. Main multiplier behind the RAM exhaustion. | `script.py:542`, `ws.js:73` | verified (code + observed tabs) |
| B3 | Slider drags queue updates: debounce is 120 ms but an update takes 1.7 s, so the server works through a backlog of stale states for up to a minute. | `auto_callback_panel.js:56` | verified |
| B4 | `ScalarChild` uses `Math.min(...values)` / `Math.max(...values)` → `RangeError` for scalar fields above ~120 k values: the quantity silently fails. | `SceneEntry.js:107-108` | verified (node: fails at 200 k) |

### Major — wrong result or resource leak

| # | bug | where | status |
|---|---|---|---|
| B5 | Initial scene delivered **twice** on page load (WS connect snapshot + `POST /load`), so all geometry is built twice. | `app_loader.js:99`, `callback_app.py:115`, `script_app.py:73` | verified |
| B6 | Callback results go only to the tab that sent the event; other tabs of the same app stay stale until reload. | `callback_app.py:150-152` | code |
| B7 | A screenshot job is claimed by whichever tab polls first — possibly an old tab or another app — so `kv.screenshot` can capture the wrong scene. All tabs poll every 400 ms forever. | `screenshot.js:195`, `script_app.py:144` | verified (polling) / code |
| B8 | Point-cloud radius slider: old instanced mesh removed but never disposed → GPU leak per slider step. | `viewer.js:144` | code |
| B9 | Scalar range slider replaces the colour attribute each step; three.js never deletes the old GL buffer → GPU leak per step. | `SceneEntry.js:198` | code |
| B10 | Point-cloud colour reverts after a radius change (`setColor` updates `e.color`, rebuild uses stale `e.opts.color`). | `viewer.js:121,141` | code |
| B11 | Tube-radius sliders of edges and curves stop after the first step: each step emits `viewer-changed`, which rebuilds the scene panel and detaches the slider being dragged. | `viewer.js:162,268`, `scene_panel.js:140` | verified |
| B12 | Messages sent while the socket is reconnecting are attached to the dead socket and lost. | `ws.js:24-27` | code |

### Minor

- B13 `show(block=True)` loops for up to 24 h if no tab ever connects (`seen` stays false).
- B14 Errors during schema capture are swallowed (`except: pass`): widgets silently missing.
- B15 Python-side state changes never reach the widgets (one-way sync); a "Reset" button cannot move sliders. Schema is captured once, so conditional widgets are static.
- B16 `_shot_done` keeps results whose collector timed out.
- B17 `setVectorLength/Radius`, `setRadius` don't emit; the panel can show stale values.
- B18 `setMaterial` per mesh does not pin; the next global Shader change overrides it.
- B19 One registration = one full scene-panel rebuild: 7 objects → 8 rebuilds per update (quadratic in object count).
- B20 `script_panel.js` is dead code.

## 3. GUI evaluation (as a user)

**Missing**
- Fit-to-scene / reset view, axis-aligned views, orthographic toggle, keyboard shortcuts (F frame, R reset, H hide). Camera near/far are fixed (0.001–100) and the grid is 4 units: scenes in other units are clipped or tiny.
- A busy indicator: during a 1.7 s update nothing shows that work is in progress.
- Colour bar on the canvas for the active scalar (only inside the panel).
- Search/filter and per-object collapse in the scene panel; "show only this".
- Undo for panel edits; a way to copy the inspect readout (it is `pointer-events: none`).

**Behaves oddly**
- The Energy panel shows "Waiting for data…" in every app, including ones without optimisation, and the click-inspect box opens on top of it.
- The Lighting folder opens by default and pushes the object list down.
- Index labels are drawn through the surface (no occlusion test) and recomputed every frame.
- ACES tone mapping changes the exact RGB colours passed from Python (a fidelity issue for figures).
- Settings live in `localStorage` per origin, i.e. per port: studio/theme/shader differ between `:8000` and `:8001`.
- Bottom-left buttons are emoji at fixed pixel offsets (assume a 280 px panel); no labels.

**Speed** (beyond §1)
- The viewer redraws 60×/s even when nothing changes (34 ms/frame with studio) in every open tab.
- Each update rebuilds every object from scratch, even when only positions changed.
- Arrow fields merge one cylinder + one cone geometry per arrow (slow for 10⁴ arrows); points use instancing, arrows should too.
- `preserveDrawingBuffer: true` permanently, only for screenshots.

## 4. Would another language help?

No full migration. The measured bottleneck is the data format and the threading model,
not Python or JavaScript: numpy already computes in C, and the browser already renders
on the GPU. Rewriting the server in Rust/C++ would leave the 27.6 MB JSON and the
blocked event loop as they are.

| option | gain | cost | verdict |
|---|---|---|---|
| binary protocol (numpy `tobytes` → `Float32Array`, no copy) | ~10× less data, no JSON parse, ~0.7 s saved per update | moderate, internal | **do it** |
| run callbacks in a worker thread | server never blocks | small | **do it** |
| Web Worker for parsing / tube building | smoother UI on huge meshes | moderate | later, if needed |
| TypeScript frontend | type safety, fewer bugs like B10/B17 | migration of ~4 000 lines | optional |
| WebGPU renderer (three.js `WebGPURenderer`) | compute shaders, lower CPU | immature for this stack | not now |
| native viewer (Polyscope C++, which kayviz replaced) | lowest memory, no browser | loses web UI, sharing, custom panels | no |

Memory floor of the browser approach: ~150–300 MB per tab plus GPU buffers. That is fine
with one tab; the risk is the tab multiplication (B2) and studio buffers.

## 5. Plan

Each phase ends with the kayviz tests, a browser check, and a commit.

**Phase 0 — commit what is done.** Glass material, save picture, memory release, save cap.

**Phase 1 — stop the freezes (small, high value).**
1. Tab reuse: before opening a tab, wait ~2 s for an existing tab to reconnect (B2).
2. Old tabs give up after the server is gone for a while and say so; no 60 fps render in a dead tab.
3. Run callbacks / sync actions in a worker thread with a lock (B1).
4. Latest-only: while an update runs, keep only the newest pending event (B3).
5. Render on demand: draw only when camera, scene, size or a setting changes.

**Phase 2 — correctness.** B4–B12, B13–B18 with a regression test each where Python-side,
and a small browser smoke test (Playwright) for the JS ones.

**Phase 3 — lean data path.**
1. Edges as index pairs into the mesh vertices; send them once (27.6 → ~8 MB as JSON).
2. Binary frames: a JSON header + raw typed arrays; the viewer builds `BufferAttribute`s
   straight from them (→ ~2 MB, no parse). Keep JSON as fallback for HTTP attach mode.
3. One scene delivery on load (B5); one panel rebuild per message (B19).
4. In-place updates when topology is unchanged (positions only).
5. Instanced arrows; drop JS copies of arrays not needed after upload.

**Phase 4 — usability.** Fit view + shortcuts + axis views; busy indicator; Energy panel
only when energies arrive; scene panel layout (Lighting collapsed, object search,
collapse); two-way widget state; occluded, cached labels; on-canvas colour bar; a
"colour-exact" option (no tone mapping) for figures; settings shared across ports.

**Phase 5 — maintainability.** Remove dead code, consider TypeScript (JSDoc types as a
first step), document the binary protocol.

### Progress (branch `debugging`)

- Phase 0 done (`1ff8528`).
- Phase 1 done: B1, B3, B6, B12, B14 fixed and the GUIApp "stop during run" bug
  (streaming actions blocked the connection) found and fixed (`499af4b`); tab reuse,
  render on demand, dead tabs giving up (`d80121e`); found on the way: the port probe
  lacked `SO_REUSEADDR`, so re-runs moved from 8000 to 8001; a returning tab of another
  app now follows the running script (`5fd7c90`). Measured on the Dupin playground: 10
  quick slider events → 2 updates, last one after 3.3 s (was a ~17 s backlog); server
  answers in 32 ms while a callback runs; idle viewer draws 0 frames.

Suggested order: 0 → 1 → 3 → 2 → 4 → 5 (Phase 3 removes the cause of several Phase 2
symptoms and is the largest speed gain).
